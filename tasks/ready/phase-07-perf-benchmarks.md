# Phase 07 — Add Rust + JS perf benchmarks for hot paths

> **Status:** ready

## Context

- With equivalence tests (phase 5) and the Rust bench framework (phase 6) in
  place, add the actual benchmark suites that compare JS and Rust performance
  on the algorithmic hot paths.
- Focus on the rendering and encoding hotspots that are plausibly expensive.
- Skip trivially cheap helpers such as validators, `compute_world_xs_and_ys`,
  and `reset_pixel_grid` unless measurement later proves they matter.

Hot-path inventory, ordered by likely cost:

1. **`rasterize`**
2. **`sdf_compound`**
3. **`compute_fill_coverage` / `compute_stroke_coverage`**
4. **`compute_final_pixel_value`**
5. **`sample_pattern_color`**
6. **`compute_shape_aabbs`**
7. **`encode_ansi`**
8. **`encode_html`**
9. **`encode_braille`**

## Decisions

1. **Use shared three-tier scene fixtures** — benchmark both languages against
   the same committed JSON scenes.

   | Tier | Canvas | Shapes |
   |------|--------|--------|
   | `trivial` | 8 × 4 (32 px) | 1 circle |
   | `typical` | 80 × 24 (1920 px) | 8 mixed shapes |
   | `heavy` | 240 × 80 (19200 px) | 40 mixed shapes |

   The fixtures live under `bench/scenes/<tier>.json` and are generated by
   `scripts/regen-bench-scenes.mjs` from a seeded source. Regen stays manual.

2. **Mirror the JS and Rust bench module layouts** — JS benchmarks live under
   `bench/methods/*.bench.mjs`; Rust mirrors them under
   `rust/benches/methods/*.rs` and aggregates them from `rust/bin/bench.rs`.
3. **Use identical benchmark name strings across languages** — matching names
   let the visualisation pair rows 1-to-1 by `name`.

   | JS | Rust |
   |----|------|
   | `bench('typical-rasterize', () => rasterize(...), opts)` | `bench("typical-rasterize", || rasterize(...), opts)` |

4. **Override iteration budgets by tier where needed** — mirror the same
   warmup/iteration counts in both languages.

   | Tier | warmup | iterations |
   |------|--------|-----------|
   | `trivial` | 100 | 5000 |
   | `typical` | 100 | 1000 |
   | `heavy` | 50 | 100 |

5. **Only optimise after measurement** — any Rust-specific optimisation must
   preserve phase-5 equivalence, show at least a 10% win on `typical` or
   `heavy`, and be documented against the benchmark that justified it.
6. **Remove inherited unrelated benchmarks** — the old `lex` / `parse` /
   `hilite` / `validate` / `roundTrip` suite is not part of
   command-line-canvas and should not remain in the hot-path benchmark set.

## Implementation

### Step 1: Create the shared bench scene fixtures

Add `bench/scenes/{trivial,typical,heavy}.json` and the generator script that
rebuilds them from a seeded source.

- It should commit the three canonical scene fixtures used by both languages.
- It should make the scene generation reproducible from a shared seeded path.
- It should produce JSON fixtures whose top-level canvas and shapes fields match
  the schema expected by both the JS and Rust hot-path entry points.

### Step 2: Add the JS hot-path benchmark modules and wiring

Create or update JS modules for rasterize, SDF compound, coverage, final pixel
value, sample pattern colour, shape AABBs, and the encoders. Wire them into
`CORE_BENCH_MODULES` and `BENCH_NAME_ORDER`.

- It should make `npm run bench:js` execute the new command-line-canvas hot-path
  benchmarks.
- It should update `CORE_BENCH_MODULES` and `BENCH_NAME_ORDER` so results sort
  deterministically.
- It should define each new `.bench.mjs` module with a `@fileoverview` JSDoc block
  and typed parameter annotations, consistent with the project's `.mjs` conventions.
- It should delete the unrelated inherited benchmark modules.

### Step 3: Add the Rust hot-path benchmark modules and aggregation

Mirror the JS coverage under `rust/benches/methods/` and aggregate the resulting
`BenchResult` lists from `rust/bin/bench.rs`.

- It should make `npm run bench:rust` execute Rust hot-path benchmarks for the
  same methods and scene tiers as the JS suite.
- It should name each Rust bench source file to match its JS counterpart
  (e.g. `rasterize.rs` ↔ `rasterize.bench.mjs`).
- It should keep file-by-file parity between the JS and Rust method sets.

### Step 4: Align shared benchmark names and tier budgets

Ensure both languages use the same `name` strings and the same per-tier warmup
and iteration counts.

- It should make the JS and Rust history CSV `name` columns match row-for-row
  after sorting.
- It should apply the same warmup/iteration overrides in both languages.

### Step 5: Apply measured optimisations only when justified

Now — and **only** now — consider Rust-specific hot-path optimisations such as
`get_unchecked`, pre-sized `String::with_capacity(...)`, or iterator-based loop
changes.

- It should preserve byte-for-byte equivalence after any accepted optimisation.
- It should keep an optimisation only when the relevant benchmark shows at least
  a 10% win on `typical` or `heavy`.
- It should document each kept optimisation with a one-line comment citing the
  motivating benchmark result.

### Step 6: Update `bench/README.md`

Describe the new hot-path methods, the shared scene fixtures, and the dual
JS/Rust benchmark layout.

- It should document the new benchmark methods and the dual-language structure.
- It should describe the three-tier scene model, the per-tier warmup and iteration
  budgets, and how to regenerate the fixture files via
  `scripts/regen-bench-scenes.mjs`.

### Step 7: Run `nvm use && npm run ok`

_(no testable behaviour)_

## Risks / notes

- **System load skew:** absolute numbers are only comparable within one machine
  and one run window; the history files are there to inspect drift over time.
- **Allocation noise:** pre-sizing strings and vectors matters for stable
  numbers, especially after warmup.

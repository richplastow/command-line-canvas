# Phase 04 — WASM bindings & top-level entrypoint

> **Status:** ready

## Context

- Expose the Rust crate to JavaScript via `wasm-bindgen`, mirroring the
  `CommandLineCanvas` class API in `command-line-canvas.mjs`.
- Both the browser-wasm and Node-wasm targets must work.
- API mirror target:

| JS | Rust (native) | Rust (wasm-bindgen) |
|----|--------------|---------------------|
| `class CommandLineCanvas` | `pub struct CommandLineCanvas` | `#[wasm_bindgen] pub struct CommandLineCanvas` |
| static `Color`, `Primitive`, `Shape` | re-export modules | `#[wasm_bindgen]` per type |
| static `version` | `pub const VERSION` | `#[wasm_bindgen(getter)] pub fn version() -> String` |
| `new CommandLineCanvas({ antiAliasRegion, background, pixels?, xExtent, yExtent })` | `CommandLineCanvas::new(opts)` | a constructor accepting one JS object, decoded into Rust fields |
| `this.canvas` | `pub canvas: Canvas` | `#[wasm_bindgen(getter)] fn canvas(&self) -> Canvas` |

## Acceptance criteria

- [ ] `npm run build:wasm-web` and `:wasm-node` produce working bundles.
- [ ] `e2e/wasm-node-equivalence.test.mjs` passes (imported by
      `test.mjs` so `npm test` picks it up).
- [ ] `dist/native/clc demo` prints something visibly canvas-like to
      stdout.
- [ ] No regression in JS-only tests.

## Observations and notes

- **`wasm-bindgen` API changes:** pin to a specific minor version in
  `Cargo.toml` (`wasm-bindgen = "=0.2.x"`). The four-ways repo uses
  `"0.2"` (caret) — consider upgrading to `=0.2.95` or whatever's
  current at the time.
- **Bundle size:** wasm output is ~kB territory for this codebase;
  enable `lto = "fat"` and `codegen-units = 1` (already in phase 1's
  `Cargo.toml`) to minimise. Add `wasm-opt -Os` post-step only if the
  size warrants it.
- **Threading:** `wasm-bindgen` does not enable threads by default. The
  current JS rasterize is single-threaded, so this is fine.
- **The `JsXxx` newtype pattern:** keeps the wasm boundary cleanly separated
  from the native API. Native Rust users see `CommandLineCanvas` directly;
  JS users see the wasm binding's flattened API.

### Static class properties → functions

JS static properties (`CommandLineCanvas.Color`) become **factory functions** on
the wasm side because `wasm-bindgen` does not support nested classes-on-classes
well. The TypeScript `.d.ts` file emitted by `wasm-pack` will document the new
shape; users update their imports.

If preserving the exact JS API surface matters, write a tiny **JS adapter** in
`dist/wasm-web/index.mjs` and `dist/wasm-node/index.cjs` that wraps the wasm
output and re-exports the static-property shape. This adapter is regenerated by
the build scripts, so the wasm-pack output stays untouched.

Default for v1: ship the wasm-pack output as-is; documenting the adapter as a
phase-5 follow-up.

### Native binary (`bin/clc`) wiring

Once the library is real, `bin/clc.rs` should accept a minimal scene description
(e.g. JSON read from stdin) and write the encoded ANSI output to stdout. Defer
the JSON parsing to a small hand-written parser or `serde_json` only if it
materially helps — otherwise, accept a fixed demo scene chosen by argv and print
its rendering, mirroring the four-ways `greet` example.

Default for v1: accept `clc demo` to print a hard-coded demo scene; full
JSON-driven mode is out of scope.

## Decisions

1. **Use a native options struct** — Rust does not have JS-style destructuring,
   so add a typed options object:

   ```rust
   pub struct CommandLineCanvasOptions {
       pub anti_alias_region: f64,
       pub background: Color,
       pub pixels: Option<Vec<u8>>,
       pub x_extent: u32,
       pub y_extent: u32,
   }

   impl CommandLineCanvas {
       pub fn new(opts: CommandLineCanvasOptions) -> Result<Self, ValidationError> { ... }
   }
   ```

2. **Hand-decode the wasm constructor input by default** — accept a `JsValue`
   and decode fields one by one before introducing `serde-wasm-bindgen`.
3. **Keep the wasm boundary isolated in `rust/wasm.rs`** — native Rust users
   see `CommandLineCanvas` directly, while JS users see a wasm wrapper.

   ```text
   rust/lib.rs                  (no change — already pubs the modules)
   rust/wasm.rs                 (new — gates everything behind cfg(target_arch = "wasm32"))
   ```

   `rust/wasm.rs` contents (sketch):

   ```rust
   #![cfg(target_arch = "wasm32")]
   use wasm_bindgen::prelude::*;
   use crate::{CommandLineCanvas, Color /* , ... */};

   #[wasm_bindgen(js_name = CommandLineCanvas)]
   pub struct JsCommandLineCanvas { inner: CommandLineCanvas }

   #[wasm_bindgen(js_class = CommandLineCanvas)]
   impl JsCommandLineCanvas {
       #[wasm_bindgen(constructor)]
       pub fn new(opts: JsValue) -> Result<JsCommandLineCanvas, JsValue> { ... }

       #[wasm_bindgen(getter)]
       pub fn version() -> String { crate::VERSION.to_string() }

       /* ... */
   }
   ```

4. **Flatten JS static properties for v1** — `CommandLineCanvas.Color` and
   similar static properties become factory functions or direct exports on the
   wasm side because `wasm-bindgen` does not model nested classes cleanly.
5. **Defer the compatibility adapter unless needed** — if exact JS API parity
   matters later, add a tiny generated JS adapter in `dist/wasm-web/index.mjs`
   and `dist/wasm-node/index.cjs`, but ship the raw `wasm-pack` surface for v1.
6. **Keep the native binary minimal** — `bin/clc.rs` should accept `clc demo`
   and print a hard-coded scene. Full JSON-driven scene input is out of scope
   for this phase.

## Implementation

### Step 1: Add `CommandLineCanvasOptions` and the native constructor

Create the options struct and make the native Rust `CommandLineCanvas::new()`
consume it.

- It should let native Rust callers construct `CommandLineCanvas` without JS
  destructuring semantics.
- It should carry `anti_alias_region`, `background`, `pixels`, `x_extent`, and
  `y_extent` through as typed Rust fields.

### Step 2: Add `rust/wasm.rs` and the wasm wrapper types

Add the wasm entrypoint layer guarded behind `cfg(target_arch = "wasm32")`.

- It should expose a wasm-facing `CommandLineCanvas` wrapper built on top of the
  native Rust type.
- It should keep the wasm-specific bindings separate from the core native API.
- It should register the module in `lib.rs` with
  `#[cfg(target_arch = "wasm32")] pub mod wasm;` so the bindings compile only
  for the wasm target.

### Step 3: Expose the JS-facing API surface

Implement the wasm constructor, version getter, model exposure, and canvas
getter using the flattened API shape planned for v1.

- It should verify that the existing `build:wasm-web` and `build:wasm-node` npm
  scripts (wired in phase 1, Step 6) produce importable bundles with the real
  library code.
- It should expose the version and constructor behaviour needed for JS-side
  smoke tests.
- It should keep the exact static-property API adapter out of scope unless it
  proves necessary. _(inferred)_

### Step 4: Add the wasm-node equivalence smoke test

Add `e2e/wasm-node-equivalence.test.mjs` that:

1. Imports the JS `CommandLineCanvas`.
2. Imports `dist/wasm-node/command-line-canvas.cjs` and reconstructs an
   equivalent Rust-backed instance.
3. Renders the same hard-coded scene with both.
4. Asserts the two `Uint8Array` pixel buffers are byte-identical.

This is a smoke test; phase 5 expands it into a full equivalence suite.

- It should pass through `test.mjs` so `npm test` exercises it.
- It should prove byte-identical pixels for the chosen hard-coded smoke scene.

### Step 5: Extend `bin/clc.rs` to render a demo scene

Once the library is real, `bin/clc.rs` should accept a minimal scene
description and write encoded ANSI output to stdout. For v1, accept `clc demo`
to print a hard-coded demo scene, mirroring the four-ways `greet` example.

- It should build the native release binary with `cargo build --release --bin clc`
  and copy the result to `dist/native/clc`.
- It should make `dist/native/clc demo` print something visibly canvas-like to
  stdout.
